# retrieval — architecture, changes, problems and fixes

> **Historical record — 2026-08-22.** The build log for this engine: what was made, every defect
> found, and what each fix measured. Kept for the measurements and the reasoning, not as current
> documentation. Module paths in it are as they were on that date. For how the engine works now,
> read [`HANDOFF-2026-08-27.md`](HANDOFF-2026-08-27.md) and [`../README.md`](../README.md).

A working record of what this engine is, what was built into it on 2026-08-22, every defect found
along the way, and what each fix was actually worth when measured.

Two rules govern everything here and are enforced as tests, not intentions:

1. **No node-type lookup tables.**
2. **No hardcoded edge weights.**

Every type and edge decision is computed against the query. Both rules exist because
`_TYPE_ORDER = {"Turn": 1, ...}` (default 5) silently demoted an entire `Fact` layer below every
turn, and `_PROVENANCE_EDGES` meant an edge type absent from a literal could never carry
relevance. A third rule emerged during this session and is now just as load-bearing:

3. **An absent measurement is not a zero.** It cost more recall than anything else on the list.

---

## 1. The pipeline

```
question
   │
L0 understanding ─► intent · cardinality · mentions · temporal + attribute constraints
   │                node/edge TYPE hypotheses (corpus-grounded)
   │                strategy WEIGHTS (floor 0.15) + EXECUTION POLICY (what actually runs)
   │
L1 candidates ───► node ANN · per-attribute ANN · bm25 · identifier · fuzzy · metadata
   │               entity resolution · ontology (type-local lexical)
   │               └─ RRF fusion, per-surface evidence preserved
   │
L2 graph ────────► relation relevance COMPUTED vs query → beam search
   │               temporal- / node- / attribute-aware traversal → paths + subgraph
   │               (or: aggregation executed as a data-engine query)
   │
L3 rerank ───────► 16 named features → intent-shaped weights → optional BGE → MMR → abstain
   │
L4 context ──────► roles + provenance → dedupe/merge → compress → budget → coverage
   │
RetrievalResult (blocks + ranked paths + trace)
```

Every layer emits a `LayerTrace`. A pipeline that reports only a final number cannot tell a
recall problem from a ranking problem, and this session turned on that distinction repeatedly.

## 2. What was built, phase by phase

### Phase 1 — L0: node-type and edge-type hypotheses

**Audited:** intent, entities, constraints and time already existed and were tested. **Node types
and edge types did not exist at all** — `QueryPlan` had no field for either.

**Built:** `text_norm.py` (shared `humanize`/`singularize`/`stem`/`content_tokens`, moved out of
`l2_graph/edge_scoring.py` which now re-exports them) and `l0_understanding/vocabulary.py`.

Types are **discovered** (`select type, count(*) group by type`) and scored as TEXT against the
question's own words: phrase match, stem-aware token coverage, answer head-noun (node types
only), plus rarity as a capped tie-break.

**The governing property: no evidence means no opinion.** If nothing in the question supports a
type, the result is EMPTY — never a ranked list of the corpus's commonest types. Verified live:
"What is Joanna allergic to?" yields `{}` on a corpus with no allergy relation, where global
profiling had confidently returned `HAS_INCIDENT`/`HAS_ATTENDEE`/`HAS_CONSUMER`.

Three traps that make such a scorer lie, all guarded:
- connective tokens fan out — `content_tokens` strips `has`/`of`/`on`, or one question matches
  all forty `HAS_*` relations;
- rarity must never propose alone — `W_RARITY (0.15) < MIN_TYPE_EVIDENCE (0.25)`;
- over-stemming invents matches (`police` must not collapse onto `policy`), under-stemming only
  loses a boost. The failure directions are not symmetric.

### Phase 2 — classification that actually changes execution

**The defect:** all eight categories (A–H) were classified correctly, and the classification
governed **nothing**. `strategies` set fusion weights with a 0.15 floor; the orchestrator ran
every surface regardless. An exact lookup paid for a full ANN sweep and a graph walk, then
down-weighted both to the floor and discarded them.

**Built:** `l0_understanding/policy.py` → `ExecutionPolicy` on `plan.policy`. Weights decide how
loudly a surface that ran gets to VOTE; the policy decides whether it RUNS.

Narrowing is only safe because of two guards:
- `MIN_CONFIDENCE_TO_NARROW = 0.5` — below it everything runs (`SEMANTIC` sits at 0.35 precisely
  because nothing was recognised, and that is the case most needing breadth);
- `widen()` — if the narrow set underfills, the skipped surfaces run after all.

Preconditions (`fuzzy` needs a mention, `metadata` a constraint, `ontology` a type hypothesis)
apply in BOTH branches, or the trace claims a surface ran that the orchestrator skipped.

**Classifier bugs found by testing the canonical example of each category:**

| category | was | cause | fix |
|---|---|---|---|
| A "What is the email of John?" | `entity` | `_ENTITY_PROFILE` matched bare "what is" | split profile frame strong/weak; the attribute frame wins |
| G "What changed between 2023 and 2025?" | `relationship` | `between` read as relational | `constraints.has_date_range()` guard |
| E "Who did Joanna talk to…" | `semantic` | verb list can never be exhaustive | `_WHO_FRAME` matches the FRAME |
| H "Count the turns by session" | not aggregation | only "count of" matched | `^count the\|all\|every` |

### Phase 2b — entity resolution wired

`EntityResolver` was finished code, never called, zero tests. Wiring it surfaced **five** defects,
two of which could not have survived a single execution:

1. every statement bound to the whole parameter bag → `ArgumentError` on the first query. Fixed
   with `_bind()` (regex must exclude `::text` casts);
2. `%%` instead of `%` — passed through literally by asyncpg, so the trigram operator was a
   syntax error;
3. a swallowed failure **poisoned the transaction**: Postgres aborts on any error, so
   `except: pass` made every LATER query die far from the cause. Optional statements must run
   inside `async with db.begin_nested()`;
4. containment scored a flat 0.8, so "Console" bound to a 62-char turn at 0.54 — and a resolved
   entity SEEDS graph expansion, so the walk started where the question never pointed. Now scaled
   by `len(mention)/len(label)`;
5. the alias lookup cost ~598ms/mention (nine OR'd JSON `LIKE '%x%'` scans) returning nothing on
   a corpus with no aliases. Now probed once per org. Resolution 1.2s → ~430ms.

### Phase 2c — aggregation executed, not stuffed

`l2_graph/aggregate.py`. Nouns parsed from the question, bound to real types via
`vocabulary.match_type` (text, never a table), then ONE grouped query. Verified: 5,882 turns;
272 sessions.

Two refusal paths, both falling back to ordinary retrieval rather than answering:
- no such type in this corpus;
- types exist but **nothing joins them** → `inconclusive`, NOT "0". `Fact` reaches `Session` only
  via `Turn`; rendering that as "0 session(s)" states a non-adjacency as a measured result.

`MAX_GROUPS` caps the LISTING, never the count.

### Phase 3 — the three branches, and attribute coverage

**Audit:** entity search worked; `ontology` was a registered surface with **no retriever**;
`dense` sat in the resolver's confidence table and was **never called**; `CandidateGraph.edges`
was declared and **never populated**.

**The headline:** `discover_attributes` genuinely accepts any field — no allow-list has ever
existed in that code. But coverage was **40 Turn nodes of ~406,000**, 5 attributes, one type. The
guarantee was true of the code and false of the data.

Fixed `index_cli` (keyset pagination — it used to `.all()` the whole selection into memory; and
resume-by-default) and indexed the corpus: **46,395 attribute surfaces across 18 attributes**,
Turn/Fact/Entity/Session/Dialogue at 100%.

`OntologySurface` ranks WITHIN implicated types (`row_number() over (partition by n.type)`) —
global lexical ranking loses a rare type to an abundant one, and this corpus is 300,070 `KeyNode`
against 1,225 `Fact`.

**Measured and rejected:** per-attribute top-k. Equal shares force room for attributes that
cannot discriminate (`speaker`, `session` at 0.05 specificity) and answer coverage fell
**38% → 25%**. Pooling lets discriminating attributes win on merit; `attribute_specificity`
handles the crowding. Do not re-try without a specificity-weighted share AND a measurement that
beats 38%.

### Phase 4 — candidate fusion

RRF and evidence-merge were structurally sound. Two defects found by measuring a live query:

1. **18 indistinguishable evidence entries.** The embedding surface runs once per query
   representation; `node_ann` recorded which one fired, `attr_ann` did not — so
   `attr_embedding/rank 0/label` appeared twice with no way to tell corroboration from a
   bookkeeping duplicate. Fixed → 0.
2. **One surface reading as three confirmations.** `attr_embedding(label), attr_embedding(text),
   attr_embedding(speaker)` looks like three-way agreement; it is one surface agreeing with
   itself, and `speaker` discriminates nothing. Fixed in `retrieved_by` — **and it immediately
   reappeared** from `optimizer.merge_equivalents`, which unioned provenance by exact tag string.
   Now one shared `group_provenance()`.

Also fixed: `fusion.rrf` defaulted an unregistered surface to weight **1.0** — higher than any
planned weight — so `identifier`, which ran on every query and was in no registry, outvoted every
deliberately-weighted surface. Now `UNPLANNED_SURFACE_WEIGHT = 0.15`.

**Fusion dedups by node IDENTITY, never by content.** A `Fact` and the `Turn` it came from can
carry identical text and are not the same evidence.

### Phase 5 — graph expansion awareness

`score_path` was the product of `edge_score` and nothing else. Three of five dimensions absent.

`l2_graph/expansion.py` → `ExpansionContext.from_plan(plan)`:
- `accepts()` — temporal rejection **before the fanout budget is spent**;
- `affinity()` — max of node-term overlap (normalised by the QUESTION's length, so a long node
  cannot become relevant by containing many words) and attribute-target match.

Invariants: an **unknown date PASSES**; affinity is bounded by `NODE_FLOOR` (0.55) and is never a
veto; `PathStep.node_score` is `Optional` where `None` = NOT ASSESSED.

Measured: "Tell me about Joanna after 2023" → `aware=node(5terms)+temporal(-247)` — 247 nodes
rejected mid-walk that previously consumed fanout.

### Phase 6 — the candidate graph as a graph

`edges` and `seeds` were written and read by nothing but a trace counter — the same
declared-but-unused defect in better disguise, and self-inflicted.

Added `adjacency()` / `neighbours()` / `dangling_edges()` and a **`connectivity`** feature: how
well a candidate sits inside the RETRIEVED subgraph. The one signal a flat list cannot produce.
Log-scaled and normalised to the best-connected candidate — a linear count lets one hub saturate
and flattens everyone else, the shape that made a PPR score poison the relevance number.

**Invariant:** edges and paths must describe the same traversal, asserted exactly
(`in_paths == in_edges`) against the live pipeline.

### Phase 7 — the learned reranker

Added `evidence_quality` (reliability × strength, best not sum — `agreement` counts HOW MANY
surfaces and cannot tell three exact matches from three trigram guesses), first-class
`rank_paths()`, and the BGE cross-encoder.

**BGE enters as ONE weighted feature among sixteen, never a verdict.** It is the sharpest signal
available (0.995 vs 0.000016 on an answering vs unrelated passage) and the component with the
worst record here — it has twice been allowed to decide and twice buried correct answers. Off by
default (~80ms/pair on CPU).

This forced the **absent-is-not-zero** contract into `score_features`: a feature missing from the
dict was NOT ASSESSED and its weight leaves the normalising mass. Without it, scoring only the
top 30 makes "outside the budget" read as "worst".

### Phase 8 — the context optimizer

dedup, compression and token budget existed. **Evidence coverage did not** — `evidence_density`
says how much was packed, never whether the packing speaks to the whole question. Added
`evidence_coverage()` (term coverage + source spread) and coverage-aware selection, with novelty
as a tie-break only.

## 3. The bug catalogue

Grouped by root cause, because the same mistake recurred in five different places.

### "An absent measurement scored as a verdict" — the most expensive class

| where | what | cost |
|---|---|---|
| `fusion.rrf` | unregistered surface defaulted to weight **1.0**, above every planned weight | `identifier` outvoted every deliberate surface on every query |
| `features.semantic` | `best("cosine")` returns 0.0 when **no dense surface looked** | a gold turn with a **0.995 keyword match ranked 189th**; 10 of 20 low-ranked golds |
| `rerank_pool = 400` | unreranked candidates fall back to `fusion_score` — a **different scale** | everything past rank 400 buried; **the single biggest recall loss** |
| `PathStep.node_score` | would have defaulted to 1.0 | avoided by design |
| `cross_encoder` | scoring the top 30 and reading absent as 0 | avoided by design |

The recurring shape: **silence about something must never be the loudest verdict.**

### The rerank cliff — the biggest single win

`Candidate.final_score` returns `rerank_score` if set, else `fusion_score`. `rerank()` only scored
the top 400 by fusion, so `ranked()` sorted **RRF scores (~0.003) against feature scores
(0.10–0.40) in one ordering**. Everything past the cut sorted below everything inside it.

Found by dumping retrieved-but-unpackaged gold turns. Their ranks: **405, 407, 408, 411, 415,
419, 419, 422, 422, 424, 428, 436, 446, 453** — every one just past 400 — on turns that directly
answer their question:

```
"Which city did John recommend to Tim?"     gold "Barcelona is a must-visit city!"   rank 411
"What is Nate's favorite genre of movies?"  gold "I love fantasy and sci-fi movies"  rank 407
```

**When failures cluster at a round number, look for a constant.**

Fix: `rerank_pool = 0` (score the whole graph). The linear reranker is a weighted sum over
already-computed features; the cross-encoder keeps its own separate pool.

### Bare entity labels took rank 1

The node whose entire text is `"Joanna"` scores `semantic=1.00 lexical=1.00` — a perfect match
carrying no information. Rank 1 in **7 of 9** probes; for "Tell me about Joanna" the whole top-8
was name fragments. This is why `recall@1` was **0.00%**, and why BGE changed nothing: the
cross-encoder scores the top 30, so its entire budget went on name fragments.

Fix: `informativeness` (weight 0.85) — the share of a node's content the QUESTION did not already
supply. Never asks what a node IS.

### Temporal blocks carried no dates

Measured on "When did Joanna make a chocolate tart?": **367 blocks, 360 carrying a `date_time`
property, ZERO showing it in the text**. The model was handed 367 undated fragments and asked
when something happened. `NOT IN CONTEXT` was the correct answer to what it was given, and every
temporal failure looked like a retrieval miss. Fixed → 246 of 247 blocks now carry their date.

### Others

- `merge_equivalents` unioned provenance by tag string → one surface listed twice.
- `attr_ann` did not record its query representation → indistinguishable evidence.
- Entity resolution: five defects (see phase 2b).
- **My own error:** `--out` rows carry a **1-BASED `idx`**; filtering with a 0-based `enumerate`
  paired every question with the wrong result. It produced a false "concurrency corrupts the
  benchmark" conclusion which I retracted. Always verify `row["question"] == suite_line["question"]`
  before trusting a derived suite.

## 4. Claim extraction

`extraction/claims.py` + `run_claims.py`. Each turn → Subject/Relation/Object/**Evidence**,
persisted as `Claim` nodes with every field its own property, linked `CLAIM_FROM` → Turn.
**2,777 claims** (conv-42 812, conv-43 949, conv-47 933) + 24,993 attribute surfaces.

Two guards are load-bearing:
- **evidence must appear verbatim in the turn** — an unsupported claim cannot be written;
- **contentfulness** — the evidence check proves the model QUOTED, not that it UNDERSTOOD. The
  first run produced `subject="that" relation="frustrating" object="."` from "Ugh, that's so
  frustrating."

**Result: claims COST ~2.4 points of node-identity recall and closed no abstraction gap.** Two
reasons, both measured: they compete with Turns for the same budget, and the anti-hallucination
guard means a claim can only RESTATE (median 67% word overlap with its source turn), never
abstract. The failing questions need exactly the inference the guard forbids.

To earn their place they need **controlled inference** — permitted to abstract, with `evidence`
as the audit trail and an explicit `inferred` flag. That is a prompt change, not an architecture
change.

**GPU reality (RTX 3050, 4GB):** `qwen2.5:7b` is 7.72GB — only 2.36GB lands on the GPU, ~70% runs
on CPU → 3.2h for 1,959 turns. `qwen2.5:3b` fits (2.37/2.90GB) → ~50 min at comparable quality.
Concurrency does not help; it is GPU-bound (12 gave the same throughput as 4).

## 5. Benchmark history

692 questions (conv-42 260 + conv-43 242 + conv-47 190), 963 evidence turns, node-identity recall.

| run | overall | note |
|---|---|---|
| v1 planner @5k | 29.28% | same-day baseline |
| v1 planner @31.5k | 38.63% | the budget its recorded 93.75% used — **not reproducible** |
| v2 @5k, no claims | 81.41% | |
| v2 @5k, claims | 79.02% | claims cost 2.4 |
| v2 @8k, claims | 79.65% | 6 better, 0 worse |
| v2 @8k + BGE | 79.65% | **identical** — metric is rank-blind |
| v2 @8k + rank fixes | 79.44% | ditto |
| **v2 @8k + rerank cliff removed** | **85.67%** | **55 better, 1 worse; zero-evidence 75 → 39** |

Final by category: Single-Hop 74.74 · Temporal 81.67 · Multi-Hop 56.92 · Knowledge 96.85 ·
Adversarial 97.09.

**The recorded 91.80%/93.75% baseline is not reproducible** — v1 reaches only 38.63% today at the
same 31.5k budget. Do not cite it until someone reproduces it.

### Metric blind spots that cost real time

- **Node-identity recall scores MEMBERSHIP, not rank.** With ~260 blocks packaged, reranking the
  top 30 reorders material already inside the set. BGE changed 65 questions' packaged sets and
  moved the score by 0.00.
- **`wf_answer_check` scores the BEST block, not the FIRST.** It reported 100% with and without
  BGE while the top block changed from a non-answer to the answer.
- Part of v2's lead over v1 is packing: 199 blocks at 24.8 tok/block vs v1's 89 at 265.

## 6. Failure inspection — read by hand, not by a 3b

The small grader disagrees sharply with a careful reader, and the gap is the whole story. On the
93 questions that fail membership recall, `qwen2.5:3b` answers **10.75% correctly from the top-20**
and the curve is nearly flat (@5 8.60% → @20 10.75% → @100 17.20%). A flat curve means the answer
is not merely ranked too low.

So I read 14 of them myself, at the same top-20 the model got:

| verdict | count | share |
|---|---|---|
| fully answerable | 4 | 29% |
| partially answerable | 4 | 29% |
| genuine retrieval miss | 6 | 43% |

Both conclusions hold, and neither alone explains the failures:

- **Retrieval genuinely misses ~43%.** "Jo" appears nowhere in 20 blocks; no April-dated hair
  turn; no book titles; the 5-October tart turn absent while four OTHER tart turns are present.
- **The 3b under-uses what it does get by roughly 3x.** For "What are Joanna's hobbies?" block #1
  is the gold answer almost verbatim — "Besides writing, I also enjoy reading, watching movies,
  and exploring nature" — and it still returned NOT IN CONTEXT. "What is Joanna allergic to?" has
  all four allergens across blocks #2, #12 and #14.

**The most diagnostic single case** is "When did Joanna make a chocolate tart with raspberries?"
Retrieval found the right TOPIC — a dozen chocolate-raspberry blocks, correctly showing their
dates after the date fix — but not the right OCCURRENCE. Nothing distinguishes "the 5 October
one" from "the 14 September one" when the question offers no other handle. Temporal questions
need the date as a FILTER, not merely as visible text.

### Why the misses miss — four distinct causes

Traced by querying the graph for each missing answer rather than assuming:

| cause | example | ours to fix? |
|---|---|---|
| the extractor took the wrong aspect of a turn | "Hey Jo, guess what I did? Dyed my hair" → we produced `Nate\|dyed\|hair`, never the address form | **yes** |
| information latent but unlinked | `Nate\|hear from\|Jo` and `Nate\|celebrate\|Jo` EXIST, but nothing states `Jo = Joanna`, and "nickname" appears nowhere in the corpus | **yes** — coreference/alias |
| the gold label needs detail its own evidence lacks | gold "dyed his hair **purple**"; "purple" is not in the labelled turn at all | no — dataset limit |
| the fact was never extracted | "A Court of Thorns and Roses" is absent from the entire graph | coverage |

`MAX_CLAIMS = 6` with a 3b model means we keep the most salient claim per turn and drop the rest.
For "Hey Jo, guess what I did?" the salient one was the hair. **Not discarding the secondary
claims is the cheapest available fix** — same extraction pass, more of its output kept.

Also measured: cross-dataset contamination is real but narrow — 2.8% of top-20 blocks across 25
questions, almost entirely concentrated in one ("Where did Joanna travel to in July 2022?" pulled
14 of 20 from synthetic enterprise reports, matching on cities and dates). Note `eval_recall.py`
scopes the v1 planner per dialogue (`ctx.scope`) and passes NO scope to workflow_v2, so v2 is
searching the whole org where v1 searched one conversation.

### Two regressions I introduced, both found by inspection

Rendering the date into each block for temporal questions defeated two length/similarity rules
downstream, because both were measuring the RENDERED string rather than the node's own statement:

1. **the content gate.** "Joanna is OK" (12 chars) became 43 with a timestamp and cleared
   `MIN_CONTENT_CHARS = 24`. The context filled with "Joanna is excited", "Nate wishes Joanna",
   "Joanna brings much joy". Fixed: gate on `cand.text`, not on the rendered block. 367 → 233
   blocks.
2. **the dedup.** Five copies of "Joanna values Nate's support" from different turns stopped
   merging: identical text scores 1.00, the same text with different dates scores **0.71**, under
   the 0.82 threshold. Fixed: `_substance()` strips the trailing annotation before comparing.

The rule both violate: **a timestamp is a label on content, not content.** Any downstream rule
that measures a block must measure its statement, not its annotations.

### Layer quality, measured

The pre-existing `Fact` layer is markedly weaker than the `Claim` layer built this session:

| | count | stative/sentiment predicate | evidence field |
|---|---|---|---|
| `Fact` (`locomo_fact_extractor`) | 1,225 | **346 (28.2%)** | none |
| `Claim` (`v2_claim_extractor`) | 2,777 | **202 (7.3%)** | yes |

Top `Fact` predicates: `thinks` 82, `has` 71, `feels` 52, `enjoys` 39, `congratulates` 38,
`is` 34, `values` 32. Roughly 30% of that layer carries no retrievable fact and competes for the
same context budget. Re-extracting those 1,225 through `claims.py` (~5 min on the 3b) both raises
the contentfulness bar and gives them the `evidence` field they lack.

## 7. Where it stands

**39 questions still return nothing.** Roughly half never reach the candidate pool; half are
retrieved and buried. Raising `candidates_per_surface` does NOT help (120 → 600 put 4 more golds
in the pool and packaged **zero**).

**Answer-level evaluation** (`benchmarks/eval_answer.py`) on the 98 failures: 17.20% answered
correctly, 16.13% correct AND grounded. Of the 40 where the model declined, **28 were actually
grounded** — retrieval delivered and generation failed to use it.

Open problems, in the order I would take them:

1. **Vacuous Facts crowd the context.** Reading the retrieved context by hand: "Joanna is OK",
   "Joanna is excited", "Nate wishes Joanna", "Joanna brings much joy" occupy the top while the
   answering turn sits outside the top 30. The `informative` feature addresses ranking; the Fact
   layer itself needs a contentfulness bar at extraction time.
2. **Some gold turns are unreachable by any retriever.** "What alternative career might Nate
   consider after gaming?" is labelled with "Turtles really bring me joy"; "What Console does
   Nate own?" with a turn naming Xenoblade but never the Switch. These need generated inference
   at ingest. Treat ~90–95% as the ceiling, not 100%.
3. **Multi-Hop (56.92%) is the weakest category** and sub-query decomposition is still inert —
   `decompose()` produces sub-queries that are only embedded, never executed.

## 8. Running it

```bash
# tests (284 unit / 66 integration)
docker compose exec api sh -c 'python -m pytest \
  opencortyx/retrieval/tests/ -q'

# membership recall — the historical metric
docker compose exec api sh -c 'python benchmarks/eval_recall.py \
  --engine workflow_v2 --suite /app/bench_tmp/locomo_692.jsonl \
  --budget 8000 --concurrency 1 --out /app/bench_tmp/out.json'

# rank-aware metrics — use this for any ranking work
docker compose exec api sh -c 'python benchmarks/eval_rank.py \
  --suite /app/bench_tmp/locomo_692.jsonl --budget 8000 --concurrency 1'

# answer-level: correct, and grounded in what we retrieved
docker compose exec api sh -c 'python benchmarks/eval_answer.py \
  --suite /app/bench_tmp/fail_new.jsonl --blocks 80 --concurrency 2'

# every layer, per question, on diverse inputs
docker compose exec api sh -c 'python benchmarks/diagnose_workflow.py --top 8'

# attribute surfaces for a slice (omit --types for every type)
docker compose exec api sh -c 'python -m \
  opencortyx.retrieval.l1_candidates.index_cli \
  --org e5954895-7b42-5a9b-93f6-911febc30bca --types Fact,Entity,Session,Turn'

# claim extraction (GPU-resident 3b; 7b does not fit 4GB VRAM)
docker compose exec api sh -c 'python -m \
  opencortyx.retrieval.extraction.run_claims \
  --org e5954895-7b42-5a9b-93f6-911febc30bca \
  --dialogues conv-42,conv-43,conv-47 --concurrency 10 --model qwen2.5:3b'
```

Iterate on `bench_tmp/fail_new.jsonl` (98 q) and `zero_new.jsonl` (39 q) — a full 692 run is
~18 min at concurrency 1 and cannot register a ranking change anyway.

Postgres is `-U axiom -d axiom`. `/app` is a bind mount of `apps/api`, so host edits are live.
